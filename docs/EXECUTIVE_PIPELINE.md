# Конвейер исполнительной документации

Для трёх баз и форм из подключённых папок см. [Библиотеки Синапса](LIBRARIES.md).
В строгом режиме формы берутся только из подтверждённых версий библиотеки.

В интерфейсе ПТО откройте **«Сообщить о работе»** (`/#/id/pipeline`).
Сообщение «Проложен кабель на участке 123» запускает сохранённое задание.
Можно ввести текст, надиктовать его кнопкой микрофона или загрузить аудиозапись.
Сообщение о выполненной работе в чате ПТО использует тот же сервис.

## Последовательность

1. Разобрать сообщение: работа, место, фактические марки, партия и явно названные даты.
2. Определить объект. Единственный объект выбирается автоматически; при неоднозначности показываются найденные варианты.
3. Прочитать индексированные тексты исходных документов объекта и документов без назначенного объекта.
   Для выбранных файлов без текста попытаться восстановить чтение через существующие OCR/зрение.
4. Сопоставить РД, шифры и листы, действовавшую редакцию, материалы, требования к качеству и испытаниям,
   нормы и последующую операцию. Дополняющие листы с разными шифрами объединяются.
5. Найти даты начала/окончания и фактические материалы в записях журнала по тому же месту **и виду работы**.
   Проектная спецификация подтверждает план, но сама по себе не доказывает монтаж.
6. Найти документы качества по точной марке, партии и известным срокам; схему по месту и работе;
   протокол по месту и требуемому испытанию. Проверить явно положительное заключение протокола.
7. Заполнить АОСР/АООК, подтянуть участников и представителей из карточки объекта и реестра назначений,
   проверить обязательные поля, сохранить черновик и связи с реальными приложениями.
8. Выдать DOCX и ZIP: акт, выбранные файлы и `manifest.json` с планом, основаниями и контрольными суммами.

Для фактов сохраняются документ, дословная цитата, номер страницы при наличии,
либо источник «сообщение», «запись работ», «уточнение пользователя».
Даты не заменяются сегодняшним числом при отсутствии основания. Дата составления акта — текущая.
Числа испытаний и результаты измерений система не придумывает.

## Уточнения и проверка инженером

Если подходят несколько сертификатов или документов РД, интерфейс показывает конкретные варианты.
Если основания нет, показывает конкретный пробел. Инженер может загрузить недостающий файл,
выбрать источник, уточнить фактическую марку/партию, место или даты и повторить проверку.
Уточнения сохраняются с автором и временем. Обновляется тот же черновик; утверждённый акт не перезаписывается.

Отрицательное или неизвестное заключение испытаний, конфликт дат/материалов, отсутствие оснований
и ошибки заполнения блокируют готовность и утверждение. Статус `ready_for_review` означает готовность
**к проверке инженером**, а не автоматическое согласование и не разрешение следующих работ.
Перед выгрузкой ZIP и утверждением проверяются файлы оснований, их статус и принадлежность объекту.
Изменившийся файл требует повторной сборки. ZIP не выдаётся частично, если приложение недоступно.
Внешняя подлинность сертификатов и достоверность полевых измерений автоматически не подтверждаются.

## API и выполнение

- `POST /api/executive/runs`: `{text, object_id?, request_id?}`, ответ 202.
- `POST /api/executive/runs/voice`: multipart `file`, `request_id`, `object_id?`.
- `GET /api/executive/runs`: последние 30 заданий организации.
- `GET /api/executive/runs/{id}`: состояние, шаги, пробелы, основания, план и файлы.
- `POST /api/executive/runs/{id}/resume`: текущая `revision`, `choices` и подтверждённые уточнения.
- `GET /api/executive/runs/{id}/bundle`: ZIP с актом и приложениями.

Задания хранятся в `IntakeEvent`; отдельная миграция не требуется. Повтор одного `request_id`
не создаёт второй акт; другой текст с тем же ключом отклоняется. Отдельные новые запросы с новым ключом
считаются отдельными заданиями. Устаревшая `revision` отклоняется.

API выполняет сборку в фоне с промежуточными сохранениями и heartbeat. Существующий планировщик
подхватывает сохранённые задания `queued` раз в минуту. Если работающий процесс не обновлял состояние
30 минут, задание получает объяснимую ошибку и допускает повтор; прежняя попытка теряет право записи.
Для восстановления после перезапуска должен работать штатный worker.

Права чтения ограничены организацией, создание и продолжение требуют `documents:write`.
Списания, складские и финансовые проводки конвейер не создаёт.

## ИИ и производительность

В `deploy/config/llm.json` и `llm.yandex.json` выделены маршруты:

- `executive_report` — разбор короткого сообщения;
- `executive_document` — извлечение фактов из исходных документов.

Инструкции требуют цитат и разделения плановых и фактических сведений. Неподтверждённые моделью
цитаты/значения отбрасываются. Извлечение работает через существующий постраничный механизм;
факты кэшируются по тексту, версии алгоритма и конфигурации моделей.
Тексты и страницы области объекта загружаются пакетно, без отдельного SQL-запроса для каждого факта.
Повторное уточнение использует кэш и тот же черновик. OCR одного документа качества не повторяется
для каждой марки в рамках одного задания.

Без подключённой модели доступны правила для структурированных текстов. Для свободных формулировок,
сканов и сложных чертежей нужно настроить LLM/OCR/vision в существующей конфигурации.
Для серверной расшифровки аудио требуется настроенный STT; при его отсутствии API возвращает объяснение.
Это настройка маршрутов и инструкций, а не обучение весов модели.

## Практические границы

Первый сценарий — одна завершённая работа на одном участке/в помещении/узле. Несколько независимых
работ следует отправлять отдельными сообщениями. Автоматическое распознавание новых назначений
из произвольных приказов в этот конвейер не добавлено: участники должны быть заведены в реестре.
Наиболее надёжно распознаются явно обозначенные места, марки и записи начала/окончания работ.
Проверка заключения протокола консервативная: нестандартная формулировка требует уточнения,
числовые пределы испытаний автоматически не рассчитываются.

Предел обработки — 80 выбранных источников РД/журналов/схем/протоколов/актов/приказов;
превышение явно блокирует полноту проверки. Документы качества подбираются отдельно по всему
доступному набору файлов объекта. ZIP ограничен 64 МБ исходных файлов, аудио — 25 МБ.
Не следует считать эти пределы проверкой всего произвольного архива без ограничения объёма.

Автотесты проверяют действительный DOCX/ZIP, даты и марки из журнала, точность участка,
неоднозначность сертификатов, сроки, изменение файлов, отрицательные/неизвестные испытания,
защиту от выдуманных фактов, доступ, голосовой маршрут, повтор и восстановление заданий.
Полный набор backend: 226 тестов прошли; сборка интерфейса и Ruff успешны.
В Chromium проверены сборка и скачивание реального ZIP, загрузка второго сертификата, выбор основания,
обновление того же акта и экран 390 px.
Браузерный стенд использует отдельную PostgreSQL и синтетические документы; точность на реальном
проектном архиве и с подключённой моделью ещё требует контрольного комплекта инженера ПТО.

Код: `backend/bis/services/executive_pipeline.py`, `backend/bis/api/executive.py`,
`backend/bis/services/executive_jobs.py`, `frontend/src/modules/executive/ExecutivePipeline.tsx`.
