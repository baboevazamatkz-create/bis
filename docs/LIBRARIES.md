# Папки и три базы Синапса

Система использует существующую PostgreSQL. Отдельная база проекта — это отдельная область доступа,
папки, источники, история и память, а не отдельный экземпляр PostgreSQL.

| Уровень | Содержимое | Для кого доступен |
|---|---|---|
| База знаний | Нормативы, стандарты, общие правила, общие бланки | Общая библиотека платформы |
| База организации | Внутренние регламенты, документы, фирменные формы и письма | Одна организация |
| База проекта | РД, ПД, журналы, сертификаты, договоры, приказы, сметы, графики | Один объект одной организации |

Организация определяется учётной записью. Активный проект выбирается сверху страницы.
При смене проекта сбрасывается рабочий интерфейс и контекст чата; история хранится отдельно.
В задаче доступны общая библиотека, документы своей организации и данные одного активного проекта.
Проектный поиск без активного проекта не просматривает все объекты.

## Подключение вечером: обычный запуск

1. Обновить зависимости backend и выполнить `bis migrate` (миграция `0006`).
2. Создать родительскую папку, например `D:/BIS-library`, с любыми удобными подпапками:

   ```text
   D:/BIS-library/
     Знания/
       Нормативы/
       Формы/
     Наша организация/
       Регламенты/
       Бланки/
     Объект А/
     Объект Б/
   ```

3. В окружении **API и worker** задать разрешённый родительский каталог:

   ```dotenv
   BIS_LIBRARY_ROOTS=["D:/BIS-library"]
   ```

   На Linux, например, `BIS_LIBRARY_ROOTS=["/srv/bis-library"]`.
   Перезапустить API и `bis worker`. Путь должен быть доступен именно процессу BIS.

4. Открыть **Библиотеки** (`/#/id/libraries`), подключить подпапки, указав их уровень,
   а для проектных папок — конкретный объект. Можно подключить несколько папок одного уровня.
   Подключение не угадывает владельца по имени папки или тексту документа.
5. Просмотреть ошибки чтения, подтвердить статус известных действующих редакций нормативов.
6. Для бланка открыть **Настроить заполнение формы**, проверить предложенные соответствия полей,
   скачать пробное заполнение и подтвердить карту этой версии.
7. Включить **строгий режим** организации. Он включается даже при пустых папках:
   отсутствие основания будет показано как пробел, а не заменено демо-нормативом или встроенной формой.

Папки организаций и проектов подключает администратор организации. Общую базу знаний — администратор
платформы. Для новой установки есть `bis create-org ... --platform-admin`. Если установлена организация
с обычным администратором, оператор сервера может явно разрешить ему управление общей библиотекой:

```bash
bis grant-platform-admin --email admin@example.ru
```

Команда принимает только существующего активного пользователя с ролью `admin` и записывает действие
в аудит. Право не выдаётся через браузер автоматически.

## Docker

Создать папку на компьютере с Docker и указать `BIS_LIBRARY_HOST_DIR`, например `/srv/bis-library`.
Запускать Compose с подготовленным дополнением:

```bash
export BIS_LIBRARY_HOST_DIR=/srv/bis-library
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.libraries.yml up -d --build
```

В интерфейсе указывать контейнерные пути: `/libraries/Знания`, `/libraries/Наша организация`,
`/libraries/Объект А`. API и worker получают один и тот же каталог **только для чтения**.
Отсутствующая папка на хосте не создаётся автоматически. Для PowerShell переменная задаётся через
`$env:BIS_LIBRARY_HOST_DIR="D:/BIS-library"` перед запуском той же команды Compose.

## Чтение и обновления

Worker проверяет подключения раз в минуту. Кнопка **Синхронизировать сейчас** запускает внеочередную
проверку. Вручную тот же штатный планировщик можно вызвать командой `bis run-jobs libraries`.

Поддерживаются PDF, DOCX, XLSX, TXT, Markdown, CSV и изображения через настроенный OCR.
Старые DOC/XLS требуют конвертации; неизвестные форматы показываются с ошибкой.
Для сканов требуется настроенный `BIS_OCR_PROVIDER`; текстовые документы читаются без облачного OCR.
Облачный ИИ разрешён, но внешние нормативные сайты и внешние документы источниками не становятся.
Векторный поиск и извлечение используют существующую конфигурацию LLM/эмбеддингов.

Каждый файл имеет контрольную сумму и неизменяемый сохранённый оригинал. Неизменившийся файл
не распознаётся заново. Изменение публикует новую версию атомарно; прежняя сохраняется в истории.
Новая версия бланка требует нового подтверждения. Переименование считается новым путём;
замену разных нормативов с разными именами файлов система не объявляет автоматически.

При подтверждённом удалении файл исключается из новых подборов. Ошибка чтения изменённого файла
не позволяет незаметно использовать старый текст. Если недоступна **вся папка**, показывается ошибка
подключения; её содержимое не объявляется удалённым. Сохранённый последний снимок остаётся доступен
до восстановления связи или явного отключения подключения. Оригинальные папки BIS не изменяет.

## Формы и конвейер

Сначала применяется подтверждённая форма проекта, затем организации, затем общей базы.
Несколько равноправных форм показываются вариантами в задании ИД. Подтверждение карты сохраняет автора,
время, контрольную сумму и версию. Отзыв подтверждения доступен в том же экране.

- DOCX: заполнение подтверждённых абзацев и ячеек с сохранением структуры таблиц и оформления первого
  текстового фрагмента. Сложную смешанную разметку внутри одного поля нужно оценить по пробному файлу.
- XLSX: заполнение подтверждённых ячеек и повторяющихся строк журнала/реестра. Формулы не перезаписываются;
  текст, начинающийся как формула, записывается как текст.
- PDF: существующие поля либо подтверждённые области `страница:x:y:ширина:высота`, в пунктах от верхнего
  левого края. Переполнение области блокирует генерацию. Для PDF с кириллицей нужен системный шрифт:
  в Docker установлен DejaVu Sans; на Windows используется Arial. При необходимости задать
  `BIS_LIBRARY_PDF_FONT` на доступный TTF.

Генерация связана с АОСР, АООК, письмами, журналами работ и реестрами ИД. Другие бланки можно хранить
и искать, но их самостоятельный сценарий заполнения в эту версию не добавлен.
Готовые сложные Jinja-шаблоны с циклами не являются картой обычного бланка: их необходимо сопоставить
с поддерживаемыми полями; несопоставленные заполнители блокируют результат.

В строгом конвейере нормативные ссылки проверяются по подключённой библиотеке. Применимые требования
к документам качества, испытаниям и виду акта могут дополняться правилами общей базы и организации,
если относятся к выполняемой работе и подтверждены дословными цитатами. Фактические даты и материалы
по-прежнему подтверждаются сообщением, журналом или явным уточнением, а не нормативным текстом.
Неподтверждённая редакция или отсутствие текста основания создают конкретный пробел.
Это поиск и проверяемое извлечение, не полная автоматическая юридическая экспертиза всех норм.

Нормативные вопросы с явными признаками требований возвращают выдержки и ссылки без добавления
нормативных сведений из памяти модели. Остальные ответы получают ограниченный контекст источников;
неверные ссылки отклоняются. Для нестандартных формулировок и сложных проектов нужен контрольный
архив для оценки качества, а не только синтетические тесты.

В акте сохраняются версии формы и нормативных оснований. Перед утверждением и ZIP проверяется,
что они не заменены и не отозваны. Подписание остаётся отдельным действием инженера.

## Старые данные и совместимость

Режим включается отдельно для организации. Пока он выключен, сохранено прежнее поведение.
После включения прежние проектные документы доступны только по своему `object_id`.
Файлы без владельца показаны администратору в **Нужно распределить**: назначить проект либо явно
отнести к документам организации. Они не становятся общими для всех объектов автоматически.
Старые диалоги без проектной привязки остаются в общем контексте, а не подмешиваются в проектные.
Миграция привязывает документную обратную связь к объекту, а неоднозначные старые факты/примеры/псевдонимы
отключает. Исходные документы миграция не удаляет.

Ограничения применяются на сервере до поиска: API, агенты, RAG, чтение документов, память, граф и кэш
поиска учитывают организацию и проект. Одного текстового указания модели для этого не используется.

## API

- `GET/POST /api/libraries`: подключения; создание требует `settings:write`.
- `PUT /api/libraries/policy`: `{strict: true|false}` для текущей организации.
- `POST /api/libraries/{id}/sync`, `PATCH /api/libraries/{id}?enabled=false`.
- `GET /api/libraries/{id}/files`: состояния и история версий.
- `GET /api/libraries/versions/{id}/file`: сохранённый оригинал.
- `POST /api/libraries/versions/{id}/prepare`: предложенная карта и адреса полей.
- `POST /api/libraries/versions/{id}/preview|approve`: `{kind, mapping}`.
- `POST /api/libraries/versions/{id}/revoke`.
- `GET /api/libraries/unassigned/list`, `POST /api/libraries/unassigned/{document_id}`.
- `GET /api/knowledge/search`: области `norms`, `organization`, `project`, `all`.
- `GET /api/knowledge/sources/{id}/file`: оригинал цитируемого источника.

Активный проект передаётся заголовком `X-BIS-Project`. Чат также принимает `object_id`;
несоответствие активному проекту отклоняется. Конвейер принимает `form_version_id` в уточнениях
либо выбранный вариант `choices.form_version_id`.

## Проверка

Полный набор backend: **247 тестов прошли** с PostgreSQL. Ruff, сборка интерфейса и проверка
конфигурации Compose с подключённым каталогом успешны.

Автотесты охватывают версии и удаление файлов, недоступный диск, ссылки на файлы за пределами папки,
ошибки форматов, отсутствие скрытого шаблона, формы DOCX/XLSX/PDF, отзыв и смену версий, нормативные
основания, правила организации, изоляцию проектов и организаций, прямое скачивание и историю чата.
В Chromium с отдельной PostgreSQL и настоящими папками проверены подключение, карта Word, пробный
файл, подтверждение, поиск по трём базам, переключение проекта и экран 390 px. Браузерные данные
синтетические; ответы API не подменялись.
