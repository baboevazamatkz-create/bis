# Матрица требований и контроль комплекта ИД

Следующий этап после [реестра фактов](PROJECT_FACTS.md): конвейер сохраняет отдельную матрицу требований и проверяет, какими выбранными приложениями они подтверждены. Это подготовка черновика для проверки инженером, а не автоматическое подписание или разрешение на последующие работы.

## Источники требований

Матрица строится из выбранной РД и подключённых библиотек: общих нормативов, регламентов организации и правил выбранного проекта. Интернет и встроенные предположения о законодательстве не используются. Для нормативного обозначения из РД в строгом режиме ищется именно указанная редакция; похожий документ из поиска её не заменяет.

Каждая строка содержит вид требования, дословное значение, цитату, источник и версию. Поддержаны вид акта, документ качества, испытание и исполнительная схема. Строка без обозначения работы наследует контекст только при однозначном виде работ и месте; смешанная спецификация требует явной привязки в цитате. Регламенты организации определяются по виду источника или названию «регламент», «инструкция», «стандарт», «норматив», СП/ГОСТ; произвольное письмо не становится нормативом.

Состояния: основание найдено, не закрыто, не прошло проверку, условное требование, не требуется по источнику, противоречие. Неизвестное условие не считается выполненным и блокирует готовность. Прямо противоположные требования не разрешаются молчаливым приоритетом папки. Для их устранения нужны уточнение области применения или корректировка подтверждённых оснований.

Есть ограничения разбора: до 100 источников за сборку, до 500 000 символов одного нормативного текста. Остаток, непрочитанный текст и неполное извлечение отмечаются явно. Эти лимиты не означают, что оставшиеся документы проверены. Признак активной нормативной редакции подтверждает пользователь; обнаружение более нового закона в интернете не выполняется.

## Связи и проверки

Для материалов сохраняется разделение плана РД, фактической записи и документа качества. Подбор проверяет точную марку и размер, тип документа, известную партию и сроки. Разные фактические партии не сворачиваются в последнюю найденную.

Протокол связывается с видом испытания и участком. Если в тексте явно указана марка, проверяется её соответствие фактическим материалам. Явные даты протокола до начала монтажа или в будущем блокируют готовность. Отрицательное либо неизвестное заключение также блокирует её. Отсутствие явно указанной даты испытания пока не компенсируется предположением из даты загрузки; это остаётся предметом проверки инженера. Для нескольких разных материалов/протоколов неоднозначность показывается как выбор документов; универсальная привязка каждого измерения к каждой жиле/линии ещё не реализована.

Матрица показывает выбранные подтверждающие документы. Общие проверки комплектности BIS, например поиск схемы, не объявляются требованиями законодательства без источника.

## Актуальность после сборки

В акте сохраняется манифест использованных РД и журналов: контрольные суммы файла и прочитанного текста, принадлежность проекту, дата, шифр, листы и редакция. До согласования и скачивания комплекта выполняется повторная проверка. Изменение журнала обнаруживается, даже если журнал не входит в ZIP приложений.

Изменение состава или редакций нормативной библиотеки требует повторной проверки требований. Проверяются также файлы использованных нормативных оснований. Новая редакция РД с тем же шифром, пересекающимися листами и датой не позже окончания работ требует пересборки. Редакция другого листа и заведомо более поздняя редакция не подменяют основание выполненных работ. Неизвестные листы/даты трактуются консервативно. Без распознанных метаданных редакции автоматическое выявление её влияния ограничено; текстовое сходство не доказывает замену листа.

Старые задания без матрицы необходимо пересобрать. Новая миграция БД для этого этапа не нужна: матрица и манифест хранятся в существующих JSON-полях.

## Интерфейс и API

В разделе «Сообщить о работе» после сборки появляется **«Контроль комплекта»**: состояние, препятствия, требования с цитатами и приложениями, кнопка повторной проверки актуальности. Результат доступен через `GET /api/executive/runs/{id}/readiness`. Чтение требует `documents:read`; задание другой организации или другого активного проекта недоступно. Запрос проверки не пересобирает акт; пересборка выполняется существующей командой повторной обработки.

## Учебный архив

Создать семь переносимых сценариев без изменения базы:

```sh
bis executive-fixtures --output ./pto-training
```

Папка должна отсутствовать или быть пустой. Команда создаёт TXT-документы, тестовые правила, `scenario.json` с ожидаемыми препятствиями и инструкцию. Сценарии: полный комплект; нет протокола; неверная партия; другая марка; спорные даты; условное требование; новая РД после сборки. В последнем сценарии новая редакция добавляется после первого выпуска по инструкции `after_build`.

Все сведения синтетические. Учебный регламент явно обозначен как пример, не является нормативным актом и не предназначен для рабочих проектов. Каждый сценарий следует загружать в отдельный тестовый проект. Для строгого режима нужна отдельно подключённая подтверждённая форма акта. Учебная папка проверяет механику; качество понимания настоящих проектов, сканов и норм требует проверки на реальном архиве и рабочей модели.

## Проверка интерфейса

Повторная проверка меняет показанный статус, если основания устарели: прежнее «Черновик готов» заменяется на «Комплект требует повторной проверки». Просмотр самого черновика остаётся доступен. Перед выдачей ZIP и согласованием сервер заново проверяет источники.

Запросы проверки привязаны к выбранному заданию и поколению запроса. Запоздалый результат или ошибка не переносятся на другое задание, включая переключение А → Б → А.

Браузерный прогон находится в `frontend/e2e/executive_pipeline.py`. Он требует Python с Playwright, Chromium и отдельный запущенный тестовый стенд с семью сценариями. Коды проектов — `PTO-<имя сценария>`, названия начинаются с `Учебный:`. На объектах должны быть заполнены участники и назначения представителей, а учебная библиотека должна иметь подтверждённую редакцию. Сценарии из генератора сами не создают объекты и назначения в базе.

```sh
BIS_UI_URL=http://127.0.0.1:5174 python frontend/e2e/executive_pipeline.py
```

Прогон создаёт черновики в учебных проектах, проверяет семь сценариев через реальный API, содержимое ZIP/DOCX, основания и мобильную ширину 390/320 пикселей. Только для проверки запоздалых ответов используется управляемая задержка/ошибка ответа в браузере. Результаты и снимки сохраняются в `BIS_UI_ARTIFACTS` (по умолчанию `/workspace/artifacts/bis-requirements-ui`). Этот прогон не предназначен для рабочего окружения.
