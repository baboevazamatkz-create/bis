# Синапс: реестр фактов и проверка перед ответом

Первый этап настройки ядра — единое хранилище утверждений из документов выбранного проекта. Чат, инструменты специалистов и конвейер ИД используют один реестр. Это изменение архитектуры и способов проверки, а не обучение весов модели.

## Что делает система

На вопрос о датах, выполненных работах, материалах, объёмах, РД, документах качества или результатах испытаний Синапс сначала определяет проект и предмет проверки. Затем проверяет реестр, дочитывает подходящие исходники, сопоставляет значения и отвечает с цитатами. Единственный проект выбирается автоматически; при нескольких доступны конкретные варианты. Короткие продолжения вроде «А когда начали?» сохраняют предмет предыдущего вопроса в рамках проекта.

Каждое утверждение хранит исходное значение, дословную цитату, документ, версию файла, контрольную сумму и страницу, если её удалось установить по реальному индексу. Данные из отчётов прораба и структурированных строк журнала имеют отдельное происхождение. Самостоятельно выпущенные конвейером акты исключены из обратного извлечения.

Разделение происхождения обязательно:

- предусмотренный проектом материал не доказывает его фактическое применение;
- сертификат подтверждает сведения документа качества, но не место укладки;
- строка учёта объёма доказывает запись о выполнении в указанную дату, но не завершение всего участка;
- результат испытаний хранится отдельно от требования провести испытания;
- отрицательные и планируемые работы не превращаются правилами извлечения в выполненные.

В интерфейсе: **Исходные данные → Факты проекта**. Доступны разбор архива, вопрос к источникам, фильтры, оригинал версии, противоречия и история проверок.

## Версии и противоречия

Повторное чтение неизменного источника сохраняет идентификаторы фактов. Изменение текста, файла, структуры страниц, вида документа или конфигурации извлечения создаёт новую версию. Старые утверждения сохраняются в истории и перестают участвовать в текущих ответах. Переиндексация немедленно помечает предыдущие снимки устаревшими. Отозванные библиотечные версии и документы другого проекта исключены до поиска.

Разные даты для одного места и вида работ показываются как противоречие, а не сворачиваются в самую раннюю или позднюю. Проверяются также невозможный период, будущие фактические даты и расхождение фактического материала с проектом. Для разных значений инженер может выбрать подтверждённое с обязательным основанием; сохраняются автор, время и история. Подмену материала и невозможный период нельзя снять простым выбором строки.

Выбор действует только для текущего состава оснований. После замены источника противоречие пересчитывается; прежнее решение автоматически не переносится. Конвейер использует подтверждённые даты и вид акта, сохраняет ссылки на решение. Перед согласованием или выдачей комплекта повторно проверяется актуальность использованного решения. Пересмотр решения или изменение источника требует повторной проверки акта.

## Охват и ограничения

Разбор выполняется с ограничением числа источников на запрос. Уже прочитанные версии используются повторно; фоновое задание `project_facts` каждую минуту постепенно разбирает архив активных проектов. Изменённые и ещё не разобранные документы обрабатываются раньше повторных попыток неудачного чтения. Готовый источник публикуется отдельной транзакцией. Занятый другим разбором источник возвращает явный неполный результат.

Непрочитанный файл, ошибка извлечения, остаток очереди или обрезка списка фактов отражаются в охвате. Ответ не утверждает отсутствие сведений, пока проверка неполная. Даже успешное извлечение означает сохранение подтверждённых цитатами утверждений, а не доказанную полноту понимания каждой страницы и чертежа.

Числовое суммирование выполняется только по структурированным строкам журнала с группировкой единиц. Упоминания одного объёма в разных документах не суммируются. Финансовые и складские расчёты остаются у профильных инструментов. Требования из РД доступны в реестре; универсальная проверка применимости всех нормативов и их редакций остаётся следующим этапом ядра.

Проверки выполнены на синтетических корпусах и в браузере с реальным API. Оценка качества на пользовательском архиве и рабочей LLM ещё необходима; текущие проверки не устанавливают точность на произвольных сканах и проектах.

## Эксплуатация и API

Миграция `0007` добавляет `fact_snapshots`, `project_facts`, `fact_conflicts`, `fact_decisions`, `brain_investigations`. Перед запуском новой версии выполнить обычное `bis migrate`. Ручной разбор доступен сразу; для фонового требуется запущенный worker. Папки подключаются по [LIBRARIES.md](LIBRARIES.md).

API под `/api/brain/facts`:

| Метод и путь | Назначение |
|---|---|
| `GET /` | Текущие утверждения, фильтры, охват |
| `POST /refresh` | Разобрать очередную порцию документов |
| `POST /investigate` | Проверить вопрос и вернуть ответ с основаниями |
| `GET /conflicts` | Противоречия и состояние решений |
| `POST /conflicts/{id}/decision` | Сохранить выбор с основанием и ожидаемой ревизией |
| `GET /conflicts/{id}/history` | История выбора |
| `GET /investigations` | История проверок проекта |
| `GET /investigations/{id}` | Детальный результат проверки |
| `GET /snapshots/{id}/file` | Оригинал версии с проверкой контрольной суммы |

Проект задаётся текущим контекстом `X-BIS-Project` либо параметром `object_id` в поддерживающих его методах. Проверки организации и проекта обязательны независимо от включения строгого режима библиотек. Чтение доступно с `documents:read`; ручной разбор и решения требуют `documents:write`. Специалисты получают инструменты `query_project_facts` и `investigate_project` в рамках своих прав.
