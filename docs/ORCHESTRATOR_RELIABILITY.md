# Надёжность поручений оркестратора BIS

База диагностики — `dde9bc14a51514ddf2d577e88091102f9b5cc5b3`. Задача охватывает чат ПТО и общие механизмы исполнения. Работа выполняется на синтетических данных с отдельным PostgreSQL.

## Фактический путь запроса

```text
Чат или SSE → api/chat._answer → организация, проект, диалог
  → Supervisor выбирает профиль → authoring_tasks восстанавливает цель и решение
  → готовый файл из истории | черновик акта | сообщение о выполненной работе | цикл Agent.run
  → инструменты с проверкой прав, аргументов и результата
  → проверка сохранённого файла → история, основания, ссылка скачивания
```

`brain/orchestrator.py` обслуживает поиск фактов по проекту. Он открывает ограниченное расследование, проверяет актуальные снимки, читает недостающие источники и учитывает решения по конфликтам. `services/executive_pipeline.py` обрабатывает сообщения о выполненной работе, а запрос на черновик использует тот же реестр фактов и стандартный генератор акта. Доступ к моделям проходит через `llm/gateway.py` с версией настроек и существующими разрешениями на данные. Делегирование использует контекст того же запроса.

## Подтверждённые проблемы и изменения

| Проблема | Доказательство | Изменение |
| --- | --- | --- |
| АОСР выпадал из памяти о подготовке документов | `authoring_tasks.intent` распознавал административные типы, а ошибочный вызов генератора приказа на синтетическом сценарии действительно сохранял приказ | Цель «АОСР» или «АООК» фиксируется отдельно. Перед записью проверяется совместимость типа с инструментом |
| Для черновика требовались фактические даты | Схема `AOSRArgs` требовала обе даты, при этом календарь принимал дату-заглушку `0001-01-01` | Черновик с разрешёнными пропусками использует значения из проверенных источников или пустые поля. Запасная дата отклоняется |
| Повторно выполнялись одинаковые вызовы | На базовом коммите инструмент чтения вызван дважды с одинаковыми параметрами и тем же отказом | Одинаковая попытка исполняется один раз. Модель получает предыдущий результат, а изменённые параметры позволяют безопасно сделать следующую попытку |
| Ссылка на файл могла выглядеть готовым результатом | Реестр черновиков проверял ссылку в БД и ключ файла без проверки содержимого | Перед возвратом проверяются вид, доступ, наличие файла и возможность открыть DOCX. Утерянный файл не инициирует новую запись |
| Поручение о черновике путалось с производственным отчётом | `prepare_executive_package` требует дословный текст отчёта. Конвейер фиксирует факты из отчёта и ждёт участок и подтверждение выполнения | У запроса на черновик отдельная ветка в существующей памяти о документах. Она не публикует факт выполнения работ |
| Возможности провайдера учитывались неполно | Модель с конфигурацией `text` получала нативные схемы инструментов | Шлюз передаёт такому провайдеру текстовое описание допустимых инструментов. Те же программные проверки действуют после разбора ответа |
| Делегированный ответ мог смешивать найденные и созданные документы | Результат делегирования содержал все переданные ссылки и текст модели | Делегирование отдельно указывает созданные в данном вызове и проверенные документы, основания и необходимость уточнения |

Отдельные гипотезы о причине конкретных ошибок на рабочей установке требуют журнала вызовов с фактическими параметрами. Синтетический сценарий доказывает поведение программы на исходном коммите и на ветке исправления при контролируемой модели. Он не измеряет качество другой версии модели или прежнего Windows-окружения.

## Контроль выполнения

- Поручение сохраняет целевой вид, проект, разрешение на пропуски, план, основания и результат в метаданных диалога. Сеанс сериализует параллельные продолжения. Подтверждение из одного диалога или проекта не действует в другом.
- План подставляет РД из относящегося к работе источника. Фактические значения из журнала требуют совпадения работы и места. Несовместимые или отсутствующие значения остаются пустыми. Готовность к утверждению не выводится из проектных данных.
- Инструменты выполняются в точках сохранения транзакции. Повтор разрешён для чтения при определённых временных сбоях PostgreSQL. При неопределённом исходе записи цикл прекращается с указанием проверить реестр.
- Для известных операций реестра после записи повторно читается запись организации и проекта. Для документов проверяются идентификатор, область и файл. Перечень расходов модели доступен только в объёме токенов, возвращённых провайдером. Чат сохраняет также время, повторное использование вызовов и число технических ошибок инструментов.

## Проверка в интерфейсе

Выберите учебный проект в «Помощнике ПТО», загрузите РД по армированию плиты и попросите подготовить АОСР. Откройте этот диалог из истории и отправьте «Создай из того, что есть, остальное я сам допишу». Скачайте черновик. Отправьте «Пришли файл» и проверьте, что вернулась та же запись. В черновике проверьте основание РД, пустые даты работ и отметку о непроверенном факте выполнения.

Строгий режим по-прежнему требует действующую утверждённую форму. Работа с резервом документов привязана к сохранённому диалогу. Данные недавно открытой беседы сохраняются после завершившейся транзакции. Маршруты и сервисы для остальных типов документов продолжают использовать существующие механизмы. Живую модель, фактические расходы API и полноту на рабочем архиве следует измерять отдельно.
