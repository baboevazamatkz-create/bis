# Подготовка документов по подключённым базам

## Исправленные причины

Раньше инструмент письма требовал зарегистрированную форму, даже если в архиве были подходящие письма. Поиск источников не был поиском образцов. Короткие продолжения диалога не имели отдельного состояния поручения, а ссылки на прочитанные документы могли выглядеть как результат подготовки. Интерфейс выводил повторяющиеся фрагменты одного документа.

Теперь корневой агент перед подготовкой распознанного административного документа получает каталог подходящих образцов. Для произвольных видов документов доступны `find_document_examples` и `create_document_draft`; письма используют `create_letter_draft`. Инструменты доступны помощнику, секретарю и ПТО, с прежней проверкой прав.

## Как работает конвейер

1. Контекст запроса определяет организацию и объект. Каталог подключений объясняет назначение баз: знания, проект, организация. Это каталог, а не утверждение, что модель прочитала весь архив.
2. Поиск выбирает доступные образцы по виду, заголовку, индексированному тексту и назначению. Приоритет — зарегистрированная форма, затем подходящий архивный документ. Не нужны фиксированные пути, имена компаний или UUID. Отключённые и заменённые версии библиотек исключаются.
3. Агент читает фактические основания отдельно от образца. `get_document` ищет по всему доступному текстовому индексу документа и отдаёт релевантные окна вместе с охватом поиска.
4. Инструмент создаёт настоящий DOCX. Из архивного DOCX переносятся параметры страницы, шрифт и подтверждённое оформление отправителя. Используется новый контейнер документа, без старого текста, получателей, дат, номеров, подписей и вложений.
5. Отсутствующие реквизиты отмечаются в черновике. Файл хранит сведения о выбранном образце, его хеше, способе адаптации и необходимости проверки.
6. Состояние поручения сохраняется с организацией и объектом. «Да» продолжает незавершённое поручение. «Где файл?» возвращает сохранённый результат без нового вызова модели. Заявление о создании без записи файла заменяется честным сообщением о незавершённой подготовке.
7. Интерфейс показывает свёрнутые основания, использованные в ответе, группирует их по документу и странице, сохраняя номера ссылок.

## Границы

- Организационные документы — образцы, а не автоматически утверждённые нормативные формы. АОСР, АООК и другие регулируемые документы сохраняют специализированный конвейер и проверки.
- Перенос оформления не гарантирует точного воспроизведения произвольной вёрстки. Для PDF, DOC и повреждённого DOCX создаётся черновик с явным предупреждением о неподтверждённом оформлении. Он не объявляется идентичным исходному бланку.
- Исходящие письма действующей базы организации используются как бланк автоматически, включая шапку-картинку в начале DOCX. Ручная регистрация формы не требуется. Для прочих образцов сохраняется проверка отправителя по карточке организации; входящее письмо само по себе не считается её бланком.
- У действующей организационной библиотеки область доступа определяется подключением, даже если импорт сохранил устаревший идентификатор проекта. Отключённые базы и неактивные версии исключаются.
- Полный поиск по индексу не означает полный OCR оригинала. Качество распознавания реальных сканов проверяется отдельно.
- Модель по-прежнему выбирает инструменты и формулирует текст; результаты требуют инженерной и юридической проверки. Дообучение не исправляет отсутствующие инструменты, поиск или сохранение состояния. Его целесообразность оценивается после проверки конвейера на репрезентативных заданиях.

## Проверки

`backend/tests/test_adaptive_authoring.py` проверяет смену организации, обновление образца, изоляцию проектов, отключение базы, распознавание образца с произвольным именем, новый вид административного документа, перенос логотипа без старой подписи, продолжение поручения и скачивание фактически созданного файла. Проверяется поиск условия в конце длинного индекса.

`frontend/e2e/compact_sources.py` проверяет сворачивание двадцати исторических ссылок в один использованный документ с двумя уникальными страницами. Эти проверки используют контролируемые данные и модель-заглушку; они не заменяют приёмку на реальном архиве пользователя и действующем API.
