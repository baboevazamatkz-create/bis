# Работа над BIS

BIS помогает инженерам ПТО вести проектные документы и исполнительную документацию. Репозиторий служит общей памятью команды. По предыдущим чатам восстанавливать контекст не требуется.

## С чего начать

1. Откройте [генеральный план](docs/PRODUCT_ROADMAP.md), [назначение проекта](docs/PROJECT_CONTEXT.md), [текущее состояние](docs/CURRENT_STATE.md) и [очередь задач](docs/TASKS.md).
2. Для изменений в коде сверяйтесь с [архитектурой](docs/ARCHITECTURE.md) и [решениями](docs/DECISIONS.md). Команды настройки и проверки находятся в [руководстве разработчика](docs/DEVELOPMENT.md).
3. Сверьте актуальный SHA `refs/heads/codex/pilot-readiness` с GitHub. Начните новую задачу в отдельной ветке от этой вершины, даже если GitHub предлагает другую ветку по умолчанию. При продолжении существующего PR используйте его ветку и сверьте её базу. Проверьте рабочую копию и сохраните чужие незавершённые изменения.
4. Получите задачу от пользователя или координатора. Новые задачи должны соответствовать утверждённому генеральному плану. Зафиксируйте результат, границы и критерии приёмки в GitHub issue, PR или [шаблоне задачи](docs/templates/TASK.md). Если приоритетов несколько, сначала сверяйтесь с очередью задач. Изменение цели или границ задачи согласуйте с пользователем. Изменение стратегического направления согласуйте с владельцем проекта.

## Работа и передача

- Посмотрите [описание ролей](docs/AI_TEAM.md) и работайте в рамках назначенной роли. При параллельной работе укажите ответственного за каждый участок и порядок объединения изменений.
- Делайте небольшие коммиты с ясной целью. Укажите в PR базу, изменения, проверенные сценарии и известные ограничения. Обновите состояние, очередь или журнал решений, если изменилась информация, на которую опирается следующая задача.
- Проверяйте основной сценарий использования, существующие данные и затронутые права доступа. Для подходящих изменений запускайте Ruff и сборку frontend. Backend-набор с БД запускайте только по [инструкции изоляции PostgreSQL](docs/TEST_DATABASE.md). Если часть проверок пропущена, укажите её и причину.
- Передайте задачу через ссылку на коммит, issue или PR. Укажите ветку, точный SHA, результаты проверок и следующий шаг по [шаблону передачи](docs/templates/HANDOFF.md). Храните общие решения и проверяемые факты в Git. Не переносите туда переписку, секреты и документы пользователей.

## Границы полномочий

Отдельное разрешение пользователя требуется для merge, смены default branch или правил защиты, удаления веток, выпуска и деплоя. Не переписывайте историю и не выполняйте force-push или разрушительные команды Git без отдельного разрешения. Не меняйте рабочий BIS, включая `C:\BIS-Pilot`, и не подключайте рабочие БД к тестам. Не запускайте рабочие миграции, сброс и очистку данных. Локальная миграция `0009` требует отдельной задачи и разрешения. Секреты, пользовательские файлы и результаты обработки храните вне Git и релизных архивов.
